# easy_GIT 설계

- 작성일: 2026-11-04
- 위치: `D:\ADE_sub\src\easy_GIT`
- 상태: 사용자 검토 대기

## 1. 무엇이고 왜 만드나

easy_GIT은 **Herdr**(코딩 에이전트용 터미널 멀티플렉서, 이 PC는 0.9.5 Windows 네이티브판)에서 쓰는 Git 보기 도구다. `D:\ADE_sub`는 Herdr용 도구들을 모아 만드는 저장소이고, easy_GIT이 그 첫 번째 도구다.

지금은 Herdr 설정에 `prefix+alt+g` → lazygit 팝업을 걸어 두고 diff를 본다. 사용자가 꼽은 불편은 하나다.

> lazygit은 파일 내용을 보기가 굉장히 불편하다. **파일 전체 내용 안에서 변경된 부분을 같이 보고 싶다.**

lazygit은 바뀐 조각(hunk)만 좁은 칸에 보여주기 때문에, 파일 전체 흐름 속에서 어디가 바뀌었는지 알기 어렵다. 사용자는 Orca(stablyai/orca)의 Git 기능을 참고 대상으로 삼았고, 그중 "파일 전체를 띄워 놓고 변경을 표시하는 diff 보기"와 "커밋 목록과 메시지 보기"를 Herdr 안에서 쓰고 싶어 한다.

## 2. 목표

1. **파일 전체 + 변경 표시.** 바뀐 파일을 열면 파일 처음부터 끝까지 보여주고, 그 안에서 추가·삭제·수정된 줄을 표시한다.
2. **두 가지 보기 방식, `v`로 전환** (사용자가 둘 다 원함)
   - **A. 합쳐 보기:** 한 칸에 파일 전체를 보여주고, 지워진 줄은 빨간 `-`, 추가된 줄은 초록 `+`로 그 자리에 끼워 넣는다. 지워진 줄에는 새 줄 번호를 붙이지 않는다.
   - **B. 좌우 보기:** 왼쪽에 이전 파일 전체, 오른쪽에 이후 파일 전체를 줄 맞춰 놓는다. 한쪽에만 있는 줄은 반대쪽에 빈 칸(빗금)을 채워 높이를 맞춘다.
3. **커밋 보기.** 커밋 목록에서 하나를 고르면 그 커밋의 **메시지 전체**(제목 + 본문, 작성자, 시각)와 바뀐 파일 목록을 보여주고, 파일은 위와 같은 방식으로 본다.
4. **작업 중인 변경 보기.** 커밋 목록 맨 위에 "● 작업 중인 변경 (N)" 항목을 둔다. 아직 커밋하지 않은 변경을 lazygit·Orca처럼 **두 묶음으로 나눠** 보여준다 (사용자 결정).
   - **Stage된 변경:** 다음 커밋에 들어갈 내용. 비교는 HEAD → index.
   - **Stage 안 된 변경:** 아직 커밋에 들어가지 않는 내용. 새 파일(untracked)도 여기 들어간다. 비교는 index → 실제 파일.
   - stage한 뒤에 다시 고친 파일은 **두 묶음에 모두** 나온다. 각 줄은 자기 비교 기준으로 diff를 보여준다. 그래서 커밋될 내용과 아직 아닌 내용을 화면에서 늘 구분할 수 있다.
5. **커밋하기** (사용자: "가능하면 좋고"). 파일 단위로 stage/unstage하고, 메시지를 입력해 "Stage된 변경" 묶음의 내용을 커밋한다. 커밋되는 것은 "Stage된 변경"에서 보이는 것과 정확히 같다.
6. **칸 크기에 맞춰 배치가 바뀐다** (§4.3).
7. **계속 켜 둘 수 있다.** 작업 폴더의 파일이나 커밋이 바뀌면 화면이 저절로 새로 고쳐진다. 에이전트 옆 칸에 띄워 두고 지켜보는 용도. *(설계자 결정)*

## 3. 목표가 아닌 것 (이번 범위에서 뺌)

Orca에는 있지만 이번에는 만들지 않는다. 사용자에게 제안했고 반대가 없었다.

- push / pull / sync
- 브랜치 전체를 기준 브랜치와 비교(Orca의 "Committed on Branch", start-from ref 비교)
- diff 줄에 코멘트를 달아 에이전트에게 보내기(Orca의 Annotate AI Diff)
- AI 커밋 메시지 생성, Fix with AI
- PR 만들기
- **변경 버리기(discard)**, **amend**: 되돌릴 수 없는 작업이라 넣지 않는다. *(설계자 결정)*
- 줄·조각 단위 stage (stage는 파일 단위만)
- 머지 충돌 해결 화면, 이미지 diff, HTML 미리보기
- 여러 저장소 동시 보기, 브랜치 전환, 다른 커밋끼리 임의 비교

### 4.2 키 (기본안, 설계자 결정)

| 키 | 동작 |
|---|---|
| ↑ ↓ | 목록·본문에서 이동 |
| Tab / Shift+Tab | 칸 사이 이동 |
| Enter / Esc | 좁은 화면에서 목록 → 본문 들어가기 / 나오기 |
| v | 합쳐 보기 ↔ 좌우 보기 |
| n / p | 본문에서 다음 / 이전 변경 위치로 이동 |
| Space | "Stage 안 된 변경"의 파일 → 그 파일 전체를 stage. "Stage된 변경"의 파일 → 그 파일 전체를 unstage |
| c | 커밋 메시지 입력 → 커밋 |
| r | 바로 새로 고침 |
| q | 닫기 |

lazygit과 겹치는 키는 lazygit 쪽 의미를 따르면 익숙하다. 세부는 만드는 사람이 정해도 된다.

### 4.3 칸 크기에 따른 배치 (사용자 확인)

| 칸 너비 | 배치 |
|---|---|
| 넓음 (예: `prefix+z`로 키운 칸) | 세 칸. 좌우 보기(B) 사용 가능 |
| 보통 | 세 칸. 좌우 보기를 고른 상태여도 **합쳐 보기로 자동 전환**. 다시 넓어지면 좌우 보기로 복귀 |
| 좁음 (에이전트 옆 세로 칸) | 한 번에 한 칸. 목록 화면(커밋 + 파일) ↔ 본문 화면을 Enter / Esc로 넘김 |

칸 크기를 바꾸면 실행 중에 바로 배치가 바뀐다. 기준 너비(몇 글자부터 넓음/보통/좁음인지)는 만들면서 실제 화면을 보고 정한다.

## 5. Herdr에서 여는 방법

- 팝업이 아니라 **칸(pane)으로 연다** (사용자 요청: "그래야 보기가 편할 것 같다").
- Herdr 설정(`%APPDATA%\herdr\config.toml`)에 다음 항목을 추가한다. `type = "pane"`은 키를 누르면 임시 칸을 열고, 프로그램이 끝나면 그 칸을 닫는다.

  ```toml
  [[keys.command]]
  key = "prefix+alt+e"          # 설계자 결정: 기존 lazygit(prefix+alt+g)은 그대로 둔다
  type = "pane"
  command = '<easy_GIT 실행 명령>'
  description = "git 보기 (easy_GIT)"
  ```

- 저장소는 **키를 누른 칸의 현재 폴더**로 정한다. 그 폴더가 git 저장소의 하위 폴더면 저장소 최상위를 찾아 연다. git 저장소가 아니면 그 사실을 화면에 보여주고 끝낸다.
- Herdr가 `type = "pane"` 명령을 어느 폴더에서 실행하는지, 칸이 어느 방향으로 열리는지는 확인이 필요하다. 현재 칸 폴더를 물려받지 않으면 `herdr pane current` 같은 Herdr CLI나 환경 변수로 알아낸다.
- 터미널에서 직접 `easy_GIT [경로]`로 실행해도 똑같이 동작해야 한다. Herdr 없이 시험할 수 있어야 한다.

## 6. 동작 규칙

- **저장소를 바꾸는 동작은 stage, unstage, commit 세 가지뿐이다.** 그 밖에는 읽기만 한다. 사용자가 키를 눌렀을 때만 실행한다.
- 커밋 전에 staged 파일이 없으면 커밋하지 않고 알려준다. 메시지가 비어 있어도 커밋하지 않는다.
- 커밋할 때 저장소의 pre-commit 훅은 평소처럼 돈다. **훅을 건너뛰지 않는다**(`--no-verify` 금지). 훅이나 커밋이 실패하면 git이 낸 출력을 화면에 그대로 보여준다.
- 파일 종류별 표시
  - 새 파일: 전체가 추가된 줄
  - 삭제된 파일: 이전 내용 전체가 지워진 줄
  - 이름이 바뀐 파일: `이전경로 → 새경로`를 보여주고, 내용 변경이 있으면 표시
  - 바이너리 파일: 내용 대신 "바이너리 파일"이라고만 표시
- 커밋을 볼 때 이전 = 부모 커밋, 이후 = 그 커밋이다. 첫 커밋은 이전이 비어 있다. 머지 커밋은 첫 번째 부모와 비교한다. *(설계자 결정)*
- 작업 중인 변경의 비교 기준 (사용자 결정, §2.4)
  - "Stage된 변경": 이전 = HEAD, 이후 = index(stage된 내용). 커밋이 하나도 없는 저장소에서는 이전이 비어 있다.
  - "Stage 안 된 변경": 이전 = index, 이후 = 작업 폴더의 실제 파일. 새 파일은 이전이 비어 있다.
- stage와 unstage는 파일 전체 단위다. 줄이나 조각 단위로 stage하는 기능은 넣지 않는다.
- 새로 고칠 때는 지금 보고 있는 커밋·파일·스크롤 위치를 가능한 한 유지한다.

## 7. 제약

- **OS:** Windows 11. Herdr는 Windows 기본 콘솔 창(conhost) 안에서 돌고 있고, Windows Terminal은 설치되어 있지 않다. conhost에서도 색과 선이 깨지지 않아야 한다.
- **Herdr:** 0.9.5. Windows에서 custom command는 `cmd.exe /d /c`로 실행된다. 테마는 nord를 쓴다. 다만 easy_GIT 색은 Herdr 테마와 꼭 맞추지 않아도 된다.
- **한글:** 파일 경로, 커밋 메시지, 파일 내용의 한글이 깨지지 않아야 한다. 이 PC의 git은 `core.quotepath=false`다. 커밋 메시지 입력에서 한글 IME 입력이 되어야 한다. Herdr 설정의 `host_cursor = "native"`는 IME 조합 위치 때문에 넣어 둔 것이다.
- **붙여넣기:** 이 환경(conhost + Herdr)에서는 Ctrl+V 붙여넣기가 안 된다는 보고가 있다. 커밋 메시지 입력이 붙여넣기에 의존하면 안 된다.
- **언어:** Python 3.12 *(설계자 결정: 이 PC에 이미 있고, 화면을 빨리 만들고 고치기 쉽다)*. 칸이 뜨는 속도가 아쉬우면 나중에 Rust로 옮기는 것을 고려한다.
- **설치된 것:** Python 3.12.9, uv, rich 14.3.2(textual 없음), Node 24, Rust 1.93, git 2.53. delta와 difftastic은 없다.
- **git 접근:** git 명령을 직접 실행해서 결과를 읽는다 *(설계자 결정)*.
- **저장소 구조:** 코드는 `src/easy_GIT/`, 테스트는 저장소 최상위 `test/` 아래에 둔다(사용자가 만든 구조). 설계 문서는 `docs/design/`에 둔다.

## 8. 성공 기준

- lazygit 대신 easy_GIT을 칸으로 열었을 때, 바뀐 파일을 **처음부터 끝까지** 보면서 바뀐 줄을 바로 찾을 수 있다.
- `v` 한 번으로 합쳐 보기와 좌우 보기를 오간다.
- 커밋을 고르면 메시지 전체를 읽을 수 있다.
- 에이전트가 파일을 고치면 켜 둔 easy_GIT 화면에 저절로 반영된다.
- 칸을 넓히거나 좁히면 §4.3대로 배치가 바뀐다.
- stage → 메시지 입력 → 커밋이 easy_GIT 안에서 끝난다.

**실패로 보는 것 (설계자 짐작):** 결국 바뀐 조각만 보여주는 화면이 되는 것, 그리고 lazygit 팝업보다 여는 게 눈에 띄게 느리거나 번거로운 것.

## 9. 만드는 사람에게 맡기는 것

- TUI 라이브러리 선택. Textual(+ 이미 설치된 rich)이 반응형 배치에 무난해 보이지만 정해진 것은 아니다.
- 설치·실행 방식: 가상환경, uv, Herdr `command`에 넣을 실행 줄.
- 좁음/보통/넓음 기준 너비.
- 자동 새로 고침 방식(파일 감시 또는 주기적 확인)과 주기.
- 문법 강조 여부.
- 커밋 목록을 한 번에 몇 개 불러올지, 더 불러오는 방식.
- 아주 큰 파일이나 줄이 아주 많은 diff를 다루는 방식.
- §4.2 키의 세부.
